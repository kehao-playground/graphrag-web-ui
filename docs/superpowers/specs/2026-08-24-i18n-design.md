# i18n Design (zh-TW + en-US)

Date: 2026-08-24
Status: revised after user code-review (B1–B3 blocking, G1–G7 gaps);
supersedes the 2026-08-23 hygiene-spec decision that "UI strings and
API error details remain zh-TW by design" — operator-facing deploy
output (helm NOTES.txt, backend logs) stays out of scope.

User decisions (2026-08-24):

1. Scope includes backend error-code mapping — stable machine codes on
   every user-visible error, localized client-side.
2. Library: react-i18next.
3. Default language: browser detection (`zh*` → zh-TW, else en-US),
   localStorage override, manual switcher.

## 1. Problem

All UI copy is hardcoded zh-TW across 12 component/page files plus
`api/client.ts`'s error fallbacks; tests assert the zh-TW strings.
Backend error `detail` values are mixed English (`"user not found"`)
and zh-TW (`"此專案已有進行中的索引任務"`) and the frontend surfaces
them verbatim, so both locales currently show mixed-language errors.
There is no locale switcher, no locale persistence, and antd's built-in
component copy (Popconfirm/Modal/Table) is left at its English default.

## 2. Goals

- Every user-visible string exists in both `zh-TW` and `en-US` catalogs;
  no hardcoded copy left in components.
- Manual language switcher (sidebar, above logout); choice persisted in
  localStorage; browser detection for first visit.
- antd internal copy follows the app locale via `ConfigProvider`
  (static `Modal.confirm` included — see §5.2).
- Every user-visible backend error response — including the two
  non-exception exits in §4.4 — carries a stable `code` (+ optional
  `params`); the frontend renders localized text by code and falls back
  to the raw `detail` string when the code is unknown (forward
  compatibility with newer backends).
- Typed i18n keys: compile-time key checking and compile-time catalog
  parity between locales.
- Test churn is bounded and named: 12 backend exact-equality
  error-body/key-set/frame assertions become field assertions (§6 — 10
  pre-existing, plus 2 that §4.3/§4.4 themselves break); all other
  existing tests stay green unchanged.

## 3. Non-goals

- Server-side translation / `Accept-Language` negotiation — the client
  localizes by code; the wire keeps a human-readable `detail`.
- Additional locales beyond zh-TW/en-US (catalog structure allows them).
- Localizing backend logs, helm NOTES.txt, or other operator output.
- FastAPI's built-in 422 validation errors (`RequestValidationError`
  shape) — the frontend never renders them today; unchanged.
- Translating the graph artifact *data* (entity titles, report text) —
  corpus content is user data, not UI copy.
- Surfacing distinct Login errors for bad credentials vs 429 —
  `Login.tsx` keeps its single fixed error copy; the
  `auth_invalid_credentials` / `auth_too_many_attempts` codes exist on
  the wire for forward use but have no UI consumer yet (recorded, not
  implemented).

## 4. Backend: error codes

### 4.1 Wire format

New `ApiError(HTTPException)` subclass + exception handler in
`api/errors.py`. Responses become:

```json
{
  "detail": "此專案已有進行中的索引任務",
  "code": "job_conflict",
  "params": {}
}
```

- `detail` keeps today's exact strings (zh-TW and English alike) —
  `detailOf` verbatim behavior and any old client keep working;
  `code`/`params` are additive fields.
- `params` is omitted when empty; values are JSON scalars (strings /
  numbers) interpolated client-side. An entry only carries `params` if
  today's `detail` already interpolates the same information
  (§5.1 invariant) — this is why `disk_watermark` has none.
- Plain `HTTPException` raised by third-party code (none user-visible
  today) renders without `code`; the frontend falls back to `detail`.
- **OpenAPI / codegen:** the error envelope is NOT declared as a
  response model — today's `openapi.json` declares no error schemas
  either (only `HTTPValidationError`), so the generated artifact is
  unchanged, the CI freshness gate needs no `gen_openapi.py` /
  `npm run gen:types` rerun, and the frontend hand-writes the envelope
  in `api/types.ts` (`ApiErrorBody { code?: string; params?:
  Record<string, string | number> }`), mirroring §4.1 per the
  AGENTS.md types.ts sync rule.

### 4.2 Code catalog

Every user-visible raise site gets a stable snake_case code (51 total).
Service exceptions that currently surface as `str(e)` gain a `code`
attribute (plus `params` where the message interpolates values); where
tests pin the exception type, new typed exceptions subclass it (e.g.
`class SettingsValidationError(ValueError)`) so existing
`pytest.raises(ValueError)` assertions stay green.

Shared / cross-route codes:

| code | status | source | params |
|---|---|---|---|
| `not_indexed` | 409 | explore + query `WorkspaceNotIndexedError` | — |
| `user_not_found` | 404 | users + projects | — |
| `forbidden` | 403 | projects/query `_forbidden` | — |

`auth` (auth_routes, deps, main.py guard — §4.4):
`auth_too_many_attempts` 429, `auth_invalid_credentials` 401,
`auth_invalid_refresh_token` 401, `auth_wrong_current_password` 400,
`auth_not_authenticated` 401, `auth_invalid_token` 401,
`auth_must_change_password` 403, `admin_only` 403.

`explore` (explore_routes): `explore_unknown_table` 404,
`explore_unsupported_filter` 422, `explore_read_failed` 502,
`explore_row_not_found` 404.

`files` (files_routes + services/files): `file_name_empty`,
`file_name_too_long`, `file_name_unsafe`, `file_name_leading_dot`
(all 400), `file_ext_not_allowed` 400 `{ext, input_file_type}`,
`file_too_large` 413 `{max_mb}`, `quota_exceeded` 413 `{quota_mb}`,
`file_not_found` 404. (`detail` phrases these as MiB; catalog values
must say MiB too, not MB.)

`jobs` (jobs_routes + services/jobs): `job_not_found` 404,
`job_conflict` 409, `disk_watermark` 409 (no params — today's detail
is the fixed string "磁碟剩餘空間不足"; the free-space numbers the UI
shows come from preflight data in the confirm modal, not from this
error), `job_already_finished` 409, `job_invalid_last_event_id` 400.

`projects` (projects_routes + services/projects):
`project_not_found` 404, `init_failed` 500, `member_owner_protected`
400 (both identical "cannot demote or remove the project owner" raises
in `set_member`/`remove_member`), `member_not_found` 404.

`query` (query_routes + services/query, rate_limit):
`query_rate_limited` 429, `query_config_failed` 500, `query_failed`
502, `query_interrupted` (mid-stream SSE event, today
`INTERRUPTED_DETAIL = "查詢中斷"`).

`settings` (settings_routes + services/settings): `settings_conflict`
409 (the JSONResponse exit — §4.4), `settings_too_large`,
`settings_invalid_yaml` `{reason}`, `settings_invalid_placeholder`
(all 400), `version_not_found` 404.

`env` (env_routes + services/env_file): `env_invalid_body`,
`env_key_value_required`, `env_value_too_large`, `env_invalid_key`
`{key}`, `env_value_single_line` (400s), `env_key_not_found` 404.

`users` (users_routes): `email_registered` 409,
`user_self_change_forbidden` 400, `user_last_admin_protected` 400.

`dry_run` (dry_run_routes): `dry_run_failed` 500.

### 4.3 SSE

The query stream's `error` event frame becomes
`{"detail": "查詢中斷", "code": "query_interrupted"}` — same additive
shape as HTTP bodies. One existing test asserts the parsed error frame
as a dict (`test_query_stream_sse.py:325`) and is rewritten per §6.
Pre-stream failures keep returning plain JSON error bodies (unchanged
mechanics). The job-log stream emits only `log`/`done` frames — no
error frame, nothing to change there.

### 4.4 Non-exception error exits

Two user-visible error paths return `JSONResponse` directly and never
reach an exception handler; both add `code` by hand:

- `api/settings_routes.py` save conflict (409
  `{"detail": "conflict", "current_content", "current_hash"}`) gains
  `"code": "settings_conflict"`. The frontend keys its conflict flow on
  `r.status === 409` (SettingsPanel), so frontend behavior is
  unchanged; the backend key-set assertion pinning this body
  (`test_settings.py:100`, and the key list in the module docstring at
  `test_settings.py:3`) is rewritten per §6.
- `main.py` `must_change_password_guard` middleware (403
  `{"detail": "password change required"}`) gains
  `"code": "auth_must_change_password"` — same code the deps.py raises
  use; one of the B1 test rewrites (`test_explore_api.py:297`) asserts
  exactly this path.

## 5. Frontend: react-i18next

### 5.1 Setup and catalogs

- Dependencies: `i18next`, `react-i18next`,
  `i18next-browser-languagedetector`.
- Catalogs are TypeScript modules, not JSON (no `resolveJsonModule`
  needed, and parity is a compile error):
  - `src/i18n/locales/zh-TW.ts` — `export default { … }` (NO `as
    const`: object keys are literal-typed already, so
    `keyof (typeof zhTW)["errors"]` is a literal union without it,
    while values stay plain `string` — no widening step to explain).
  - `src/i18n/locales/en-US.ts` — same tree, checked against the
    zh-TW shape via `satisfies` (deep `Shape<T>` mapped type), so a
    missing or extra key in either locale fails `tsc -b`.
  - Sections per feature: `common`, `layout`, `login`, `projects`,
    `projectDetail`, `adminUsers`, `files`, `jobs`, `query`, `explore`,
    `graph`, `settings`, `errors`. `errors.*` mirrors §4.2 exactly.
- i18next init in `src/i18n/index.ts`:

```ts
i18n.use(LanguageDetector).init({
  supportedLngs: ["zh-TW", "en-US"],
  fallbackLng: "en-US",                     // missing-key backstop only
  detection: {
    order: ["localStorage", "navigator"],
    caches: ["localStorage"],
    convertDetectedLanguage: resolveDetectedLanguage,
  },
  interpolation: { escapeValue: false },    // React escapes already
  resources: { "zh-TW": { translation: zhTW },
               "en-US": { translation: enUS } },
});
```

- Language resolution is an explicit pure function, not i18next
  negotiation:

```ts
export function resolveDetectedLanguage(l: string): "zh-TW" | "en-US" {
  return l.toLowerCase().startsWith("zh") ? "zh-TW" : "en-US";
}
```

  Navigator → resolved (this table is the unit test):
  `zh-TW`/`zh`/`zh-CN`/`zh-HK`/`zh-Hant` → zh-TW; `en-US`/`en`/`en-GB`
  → en-US; `fr-FR`/`ja-JP`/anything else → en-US. A cached
  localStorage value passes through the same function. No
  `nonExplicitSupportedLngs` (its region-stripping semantics don't do
  what this needs); no zh-TW fallback (would contradict decision 3 —
  non-zh first visits must land on en-US).
- Both catalogs are bundled (no lazy chunks — two small modules).
- Typed keys: `CustomTypeOptions.resources` points at the zh-TW module
  (no `as const` anywhere, so values are `string` and `t()` returns
  `string`); `type ErrorCode = keyof (typeof zhTW)["errors"]`.
- **Catalog invariant:** where a zh-TW wire `detail` exists today, the
  zh-TW catalog value equals it verbatim — because `detailOf` prefers
  code→catalog, this is what keeps zh-TW rendering byte-identical.
  Entries with `params` must interpolate exactly the information in
  today's detail. Previously-English details get proper zh-TW
  translations (this also fixes today's mixed-language zh-TW UI);
  en-US values are new translations throughout.

### 5.2 antd wiring

`App.tsx` wraps the tree in `ConfigProvider` with
`locale={lang === "zh-TW" ? antdZhTW : antdEnUS}` (from
`antd/locale/zh_TW` / `antd/locale/en_US`), driven by
`useTranslation()`. antd has no date-picker usage here, so no dayjs
locale wiring is needed. Static `Modal.confirm` (JobsPanel) needs no
`<App>` wrapper: a mounted `<ConfigProvider locale>` activates it —
antd's locale receiver calls `changeConfirmLocale()` from a
`React.useEffect` while mounted (registering on mount, popping the
list on cleanup — `antd/es/locale/index.js:19-22`), and static calls
read that module-level runtime locale. Render-time activation suffices.
(Panel tests mount without ConfigProvider, so static confirm copy
stays antd's default `en_US` there — exactly as today, no test churn.)

### 5.3 Switcher

`Layout.tsx` sidebar, above the logout menu: a `Segmented` control with
`中文 / English`. On change: `i18n.changeLanguage(...)` (detector
persists to localStorage) and `document.documentElement.lang` /
`document.title` sync (a11y + browser translate prompts;
`index.html`'s hardcoded `lang="zh-Hant"` is replaced by this runtime
sync). Dates rendered via `toLocaleString` switch to the active locale
(`new Date(v).toLocaleString(i18n.language)`), so the chosen language —
not the browser — decides the date format.

Known limitation, recorded: React Query caches a thrown
`Error.message` as an already-formed string; errors visible at switch
time keep the old language until refetch/retry. Accepted — no
cache-busting machinery for this.

### 5.4 Error surfacing (`api/client.ts`)

One shared code→catalog function, three consumers:

```ts
export function messageOfBody(
  body: Record<string, unknown>, fallbackKey: string,
): string {
  const code = body.code;
  const isErrorCode = (c: string): c is ErrorCode => c in zhTW.errors;
  if (typeof code === "string" && isErrorCode(code)) {
    return i18n.t(`errors.${code}`, body.params ?? {});
  }
  if (typeof body.detail === "string") return body.detail;   // verbatim
  return i18n.t(fallbackKey);
}
```

- `detailOf(r, fallbackKey)` / `requireOk(r, fallbackKey)` become thin
  wrappers (`messageOfBody(await bodyOf(r), fallbackKey)`); callers
  pass i18n fallback keys (`{status}` interpolated) instead of
  hardcoded zh-TW strings.
- `SettingsPanel.tsx`'s four direct `bodyOf(r).detail` reads (:43
  load, :108 save, :128 dry-run, :143 env set — the 409 conflict read
  also needs `current_content`/`current_hash`, so it keeps `bodyOf`
  for data and routes only the message through `messageOfBody`).
- `QueryPanel`'s SSE `error` handler maps `code` the same way.
- The user-defined type guard (not a bare `code in zhTW.errors` — TS
  `in` narrowing applies to the object operand, not the key — and not
  `i18n.exists`, which returns `boolean` without narrowing) is what
  makes `errors.${code}` typecheck without casts; unknown codes fall
  through to the verbatim `detail`.
- `humanDuration` (JobsPanel) composes translated unit words
  (`jobs.durationUnitSecond` etc.) — no plural forms needed (CJK has
  none; English "1 min" vs "2 min" reads fine without pluralization).

### 5.5 Copy extraction

Every hardcoded zh-TW string in the 12 component/page files plus
`client.ts` moves to the catalogs (~150 keys). The `zh-TW.ts` catalog
values are today's exact copy (tests depend on it); `en-US.ts` is newly
translated. Comments in code stay English per AGENTS.md.

## 6. Tests

Backend (`uv run pytest`):

- Existing `detail` assertions stay, but 12 exact-equality assertions
  change to field assertions — the 10 pre-existing error BODY ones
  (`test_explore_api.py` 9: lines 147, 175, 181, 258, 266, 269, 280,
  297, 306; `test_projects.py:122`) plus 2 broken by this design's own
  §4.3/§4.4 additions (`test_settings.py:100` key-set, with the module
  docstring key list at `test_settings.py:3`;
  `test_query_stream_sse.py:325` parsed error-frame dict):

  ```python
  body = r.json()
  assert body["detail"] == "未知的資料表"
  assert body["code"] == "explore_unknown_table"
  ```

  Field assertions, not dict equality — adding a future envelope field
  must not re-break them.
- New: unit test for the ApiError constructor/handler shape; assertions
  that each §4.2 route emits the expected `code` (representative
  happy-path-per-code where cheap); both §4.4 exits carry their codes.

Frontend (`npm test`):

- `setupTests.ts` imports the i18n module (self-initializing — there
  is no `lng` to inject) and then runs `await
  i18n.changeLanguage("zh-TW")` at setup time (vitest setupFiles
  support top-level await). Strictly, the detector DOES run at import
  under jsdom (`navigator.language` = `en-US` → resolves en-US); the
  setup override discards that before any test executes — without it
  every existing zh-TW assertion flips. All existing tests keep
  passing unchanged.
- Test isolation: `afterEach(() => i18n.changeLanguage("zh-TW"))` —
  switcher tests must not leak language across tests/files (the
  detector caches each change to `i18nextLng`; jsdom resets
  localStorage per test file, so cross-file leakage is already
  impossible — the reset is for within-file leakage).
- New tests:
  - `resolveDetectedLanguage` table test (§5.1 navigator table).
  - Switcher toggles rendered copy (and `document.documentElement.lang`).
  - `messageOfBody`: code + params in both locales; unknown code falls
    back to verbatim `detail`; neither → fallback key.
  - Locale parity: `zh-TW.ts` and `en-US.ts` expose identical key trees
    (deep key-set equality) — compile-time `satisfies` is primary;
    this runtime test is the backstop.

## 7. Sequence

1. Backend: `api/errors.py` (ApiError + handler), convert raise sites,
   service exception `code`/`params` attributes, §4.4 JSONResponse
   exits, SSE error frame; rewrite the 12 exact-equality assertions;
   backend tests.
2. Frontend: i18n init + catalogs + typed keys + ConfigProvider +
   switcher + `documentElement` sync; extract copy per component;
   `messageOfBody` + `detailOf`/`requireOk` + SettingsPanel/QueryPanel
   wiring; pin tests to zh-TW + isolation reset; new tests.
3. Verify: `uv run pytest`, `uv run ruff check`, `npm test`,
   `npx tsc -b --noEmit`, `npm run build` (no `gen_openapi.py` /
   `gen:types` rerun — §4.1); browser-drive the built app through both
   locales (login, projects, jobs modal, files upload error, query
   error, settings conflict) confirming localized copy end to end.
